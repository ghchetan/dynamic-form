Accurex Dynamic Form

Business users design a form in the CRM. The CRM API sends that design as JSON. This package turns the JSON into a working form on the corporate website. You don't write any HTML for a form.

CRMBusiness users configure fields, rules and buttons
→
API (JSON)One form configuration, e.g. the start-up report
→
DynamicFormRendererReads the JSON and builds the page
→
WebsiteTechnicians fill it in, online or offline

The sample in this package is the Accurex Start-Up Report, which technicians fill in on site when commissioning kitchen ventilation equipment. Each piece of equipment is a unit: control panels (CP-1), hoods (HD-1), exhaust fans (EF-1) and make-up air units (MUA-1). Each unit has checks such as "Power to control panel?" and readings such as "Motor amp draw: 12.9 A against a nameplate FLA of 12.4 A". The form judges every answer as Pass Check Flagged or — (not answered) and lists every problem in one place before the report is submitted.

What the package does

  • Draws the form from JSON: 10 field types, 4 section types, unit tabs, a header and an action bar.
  • Judges answers: it checks answers against rules from the config (expected value, tolerance in %, exact match, value map, and conditions such as value > expectedHours * 0.25).
  • Rolls up status: progress chips ("3/7"), a coloured dot per unit, and a deficiency list with a View link that jumps to each problem.
  • Runs workflow: save draft, email, print, timer, "Pull from CAPS", Submit for review, and Approve / Reject.
  • Works offline: drafts with photos, an outbox that sends reports when the connection returns, and a service worker so the page itself opens without a network.

Get started

Quick start

Put the sample start-up report on a page and run it locally. This takes about five minutes.

  1. Copy the package

    Copy these into the website, keeping the folder structure:

    Accurex-DynamicFormRenderer.js   ← the file the page loads
Accurex-dynamic-form.css
service-worker.js                ← only if you want the page to open offline
src/                             ← all the framework code

  2. Add the stylesheet, the script and a container

    your-page.html
    <link rel="stylesheet" href="Accurex-dynamic-form.css">

<div id="formHost"></div>

<script type="module" src="Accurex-DynamicFormRenderer.js"></script>

    Pitfall

    type="module" is required. Without it, the browser can't load the files under src/ and the page shows nothing.

  3. Create the form and render it

    your-page.html
    <script>
  document.addEventListener('DOMContentLoaded', async () => {
    const form = new DynamicFormRenderer({
      container: '#formHost',
      configUrl: '/api/forms/startup-report',   // the CRM API that returns the JSON
      serviceWorkerUrl: 'service-worker.js',    // optional: open offline
      onWorkflow: (action, data, form) => form.submit(),
    });
    await form.render();
  });
</script>

    This is a normal (non-module) script, which is why it uses window.DynamicFormRenderer by its plain name. Module scripts run before DOMContentLoaded, so the class is always ready by then.

  4. Serve it over http

    Opening the HTML file directly (file://) doesn't work: browsers block modules and fetch() there. In the package folder, run the development server:

    python3 dev-server.py

    Then open http://localhost:8080/sample.html. The dev server also stands in for the CRM's POST /api/startup-report, so Submit, Approve and Reject work, and every report it receives is printed in the terminal.

  5. Try it

    • On CP-1, answer No to "Power to lights?". The chip turns Flagged, the unit tab gets a red dot, and the deficiency box at the top lists it. Click View to jump back.
    • Enter 18.2 and 19.5 in "EF Fan 1 overload setting". That's a 7.1% deviation: Check.
    • Click Save draft, reload, and the answers come back with a "Draft restored" banner.
    • Click Submit for review and watch the dev server's terminal.

Four kinds of building block

Almost everything you will add fits one of four kinds. Each kind has a registry: a plain object that maps the type written in the JSON to the code that handles it.

To add a new one, you write one file and add one line to the registry. Nothing else in the framework changes. Add a field type walks through it.

House rules

  • One source of truth: values live only in form.values. Fields never keep their own copy.
  • No innerHTML with config text: build elements with el() from src/utils/dom.js, which uses textContent.
  • Comment the why: every file starts with a comment saying what it is for and showing a config example.

How the form thinks

The whole framework follows one loop. Once you know it, you can find your way around any file.

You will learn

  • Where every value is kept, and why there is only one place
  • What happens, step by step, when a technician taps a button

The loop

user inputtypes, taps, picks a photo
→
form.setValue()the only way to change a value
→
form.valuesone object: name → value
→
form.refresh()everything redraws from values
→
screenchips, dots, lists, totals
↺ and back to the user

All values live in one object, form.values. A field never keeps its own copy. When you debug, there is exactly one place to look:

browser console
form.values.u4LightsPower        // "No"
form.values.u4OverloadReading    // "19.5"
form.values.reportStatus         // "draft"

Following one tap

A technician on CP-1 taps No for "Power to lights?". Here is everything that happens, in order.

  1. The button calls setValue

    The SegmentedField built that button with a click handler. It calls the form, nothing else:

    src/fields/SegmentedField.js
    button(option.label, 'dfr-seg-btn', () => this.form.setValue(this.name, option.value))

  2. setValue stores it, tells the website, and refreshes

    src/DynamicFormRenderer.js
    setValue(name, value, { notify = true } = {}) {
    this.values[name] = value;
    if (notify) this.callbacks.onFieldChange?.(name, value, this.getField(name)?.config || null, this);
    this.refresh();
}

  3. refresh runs three steps

    src/DynamicFormRenderer.js
    refresh() {
    // Step 1: calculated fields work out their numbers first
    this.fields.forEach(field => field.recalculate());
    // Step 2: every field updates its own look
    this.fields.forEach(field => field.refresh());
    // Step 3: every widget updates what it collects from many fields
    this.widgets.forEach(widget => widget.refresh?.());
}

  4. The screen catches up

    • The field: its chip shows Flagged and the No button turns red.
    • The Control Panel accordion: its chip shows a red "1/7".
    • The CP-1 tab: its dot turns red.
    • The deficiency box: it turns red and lists "Power to lights? · CP-1 · RED · View".
    • The header: "Open deficiencies" shows "1 item".

Fields and widgets

Two kinds of things refresh.

KindWhat it isExample
FieldOne question in the form. An object made from a class in src/fields/. Knows its config, its form and where it sits."Power to lights?"
WidgetAny block that shows information collected from many fields. A plain object { element, refresh } registered with form.addWidget().Deficiency list, accordion progress chip, unit tabs, header metrics
Why redraw everything after every change?

Targeted updates ("this field changed, so update these three things") are faster, but every new feature must remember which things to update. That is where bugs come from. Refreshing everything is simple and always correct. The sample form has 85 values, so a full refresh takes well under a millisecond.

There is one place where it matters: the site timer refreshes the form every second. The deficiency list and the equipment summary therefore compare a short "signature" of what they would show, and only rebuild when it changed. Otherwise the View buttons would be replaced under the user's finger mid-click.

Pitfall

Inside recalculate(), write to this.form.values directly, never with setValue(). setValue() calls refresh(), which calls recalculate(), which calls setValue()... and the page freezes.

Try it yourself

Challenge: change a value from the console. Does the screen update?

Run form.values.u4Mark = 'CP-9'. The tab still says CP-1, because nothing called refresh(). Now run form.refresh() and the tab updates. form.setValue('u4Mark', 'CP-9') does both in one call. That is why code should always use setValue.

Recap

  • Values live in form.values, and only there.
  • Change values with form.setValue(name, value).
  • refresh() runs three steps: recalculate, refresh fields, refresh widgets.

Statuses and deficiencies

How one answer becomes a colour, and how colours roll up to sections, units and the deficiency list.

You will learn

  • The four field statuses and where they come from
  • What makes a field "tracked", and what "complete" means for each type
  • The exact rules for section chips and unit dots

Field status

StatusChipMeaning
greenPassThe answer meets the rule.
yellowCheckClose to the limit; someone should look.
redFlaggedThe answer fails the rule: a deficiency.
gray—Not answered yet, or nothing to judge (e.g. N/A).

A field gets its status from the first of these that applies:

  1. No answer → gray.
  2. The field has statusRules → the first rule whose condition is true.
  3. The field has an evaluation → the evaluator named in evaluation.type.
  4. Otherwise → gray.

Tracked and complete

A field is tracked when its config has an evaluation block. Only tracked fields count in progress chips and can appear in the deficiency list. This depends on the config, not on the field type: a dropdown with a valueMap evaluation is tracked; a plain text box isn't.

Field typeCounts as complete when
checkboxTicked (true).
toleranceBoth reference and reading are numbers.
all othersThe value is not empty. "N/A" is an answer, so it counts as complete.

statusRules only colour

A field with statusRules but no evaluation (like the hours Variance) changes colour but is not tracked. Running 30 minutes over the expected time is not an equipment deficiency.

Section chips

Each accordion shows completed/total for its tracked fields. Its colour is the first that applies:

RuleChip
any field red2/7
any field yellow5/7
all complete7/7
otherwise3/7

Unit status

Shown as the dot on each unit tab, on the Summary tab, and in getData().units. The first rule that applies wins:

Rulestatuslabel
any tracked field redfailRed — deficiency found
any tracked field yellowcautionYellow — needs a look
nothing answered and no notespendingNot started
some tracked fields not completependingIn progress
everything completepassGreen — no issues

Writing unit notes counts as "started", so a unit with only notes shows In progress.

The deficiency list

Every tracked field that is red or yellow, unit by unit in tab order, with the unit's mark (its name, e.g. EF-1) and a View button. View switches to the right tab, opens the accordion, scrolls to the field and flashes it. The same count feeds the header metric "Open deficiencies" and the email placeholder {deficiencyStatusText}.

Where does the unit name ("mark") come from?

From the unit's identity field whose name contains "mark" (case-insensitive), e.g. u2Mark. The technician can rename a unit by editing that field, and every tab, summary row and deficiency line follows. Without such a field, the tab label is used.

Recap

  • evaluation both colours a field and makes it tracked; statusRules only colours.
  • Red beats yellow beats complete, at every level.
  • The rules live in plain functions in src/core/status.js, with no page code, so they are easy to read and test.

What you get for free

Extend BaseField and you already have: the label, the "?" help box, the optional status chip, the "Attach photo" button, the default value, status from evaluation/statusRules, progress tracking, and grid placement. Usually you only write renderControl() and sometimes refresh().

  1. Create the class

    src/fields/RatingField.js
    import { el, button } from '../utils/dom.js';
import { BaseField } from './BaseField.js';

/**
 * RatingField — a score from 1 to `max` (default 5), shown as a row of buttons.
 *
 * Config example:
 *   { "type": "rating", "name": "u3FilterCondition", "label": "Grease filter condition", "max": 5 }
 */
export class RatingField extends BaseField {
    constructor(config, form, context) {
        super(config, form, context);
        this.showsStatusChip = true;   // show Pass / Flagged when the config has an evaluation
        this.scoreButtons = [];
    }

    /** Several buttons, no single input for the <label> to point to. */
    labelTargetId() {
        return null;
    }
}

  2. Draw the control

    renderControl() returns the element that goes under the label. Clicking a button calls setValue, exactly like every other field.

    src/fields/RatingField.js
    renderControl() {
    const max = this.config.max || 5;

    for (let score = 1; score <= max; score++) {
        const scoreButton = button(String(score), 'dfr-seg-btn', () => this.form.setValue(this.name, score));
        this.scoreButtons.push(scoreButton);
    }
    return el('div', { className: 'dfr-segmented' }, this.scoreButtons);
}

  3. Show the current value

    refresh() runs after every change. Call super.refresh() first so the chip and photo picker update, then add your own part.

    src/fields/RatingField.js
    refresh() {
    super.refresh();
    const current = Number(this.value || 0);
    this.scoreButtons.forEach((scoreButton, index) => {
        scoreButton.classList.toggle('is-active', index < current);
    });
}

  4. Register it

    src/fields/index.js
    import { RatingField } from './RatingField.js';

export const FIELD_TYPES = {
    // ...the existing types
    rating: RatingField,
};

  5. Use it in the JSON

    { "type": "rating", "name": "u3FilterCondition", "label": "Grease filter condition", "max": 5 }

    To give it a pass/fail rule, add an evaluator. The next page adds minimumScore.

Register from the website instead

If you can't edit the package (for example it's shared between sites), the registries are exported. Register before render():

your-page.html
<script type="module">
  import { FIELD_TYPES, BaseField } from './Accurex-DynamicFormRenderer.js';

  class RatingField extends BaseField { /* ... as above ... */ }
  FIELD_TYPES.rating = RatingField;
</script>

Module scripts run in order and before DOMContentLoaded, so the type exists by the time the page calls render().

A field that stores more than one value

Override getDefaultValues() and return every name. The form registers each name, so form.getField(name) and onFieldChange work for all of them. ToleranceField does this for its reference and reading:

getDefaultValues() {
    const { reference, reading } = this.config;
    return {
        [reference.name]: reference.defaultValue ?? '',
        [reading.name]: reading.defaultValue ?? '',
    };
}

Then also override isComplete() and getStatus(), because the base versions look at this.value (the single value under this.name).

Pitfall

If you set this.control, the base refresh() copies form.values[this.name] into it with setInputValue(). That's right for inputs, selects and textareas. For anything else, leave this.control as null or override syncControlValue().

Recap

  • Extend BaseField; override renderControl() and, when needed, refresh().
  • Change values only with this.form.setValue().
  • One line in FIELD_TYPES makes the type available to every config.

A pass/fail rule

An evaluator receives the evaluation object from the JSON and the field's answer, and returns 'green', 'yellow', 'red' or 'gray'.

src/evaluators/index.js
export const EVALUATORS = {
    // ...the existing rules

    /** Pass when the score is at least `minimum`, e.g. { "type": "minimumScore", "minimum": 3 }. */
    minimumScore(rule, value) {
        return Number(value) >= rule.minimum ? FIELD_STATUS.PASS : FIELD_STATUS.FAIL;
    },
};
{ "type": "rating", "name": "u3FilterCondition", "label": "Grease filter condition",

A section

A section function receives the form and the section's config, and returns { element }. Add refresh only when the section shows information that changes with the answers.

src/sections/noticeSection.js
import { el } from '../utils/dom.js';

/**
 * Notice — a box of instructions, e.g. a safety reminder.
 * Config: { "type": "notice", "title": "Before you start", "text": "Lock out power at the panel." }
 */
export function renderNotice(form, section) {
    const element = el('section', { className: 'dfr-card' }, [
        el('h3', { className: 'dfr-card-title', text: section.title }),
        el('p', { className: 'dfr-smallnote', text: section.text }),
    ]);
    return { element };   // nothing changes, so no refresh
}

Two ways to colour a field. evaluation is a named rule and makes the field tracked. statusRules is a list of conditions and only colours.

evaluation

PropertyTypeDefaultDescription

Rule types

typeOptionsResult
expectedValueexpectedValue, passStatus (green), failStatus (red), notApplicableStatus (gray)Answer equals expectedValue → passStatus; "N/A" → notApplicableStatus; anything else → failStatus.

PropertyTypeDefaultDescription

JavaScript API

Instance methods

What the website (or your own extension code) can call on a form.

Life cycle

render() → Promise<this>

Loads the configuration, builds the form, restores a draft, and starts offline syncing. Calling it again rebuilds the form from scratch (timers and syncing from the previous build are stopped first). Throws if the config can't be loaded or has no id.

try {
  await form.render();
} catch (error) {
  host.textContent = 'The form could not be loaded. Please refresh.';
  console.error(error);
}

destroy()

Stops site timers and offline syncing, and empties the container. Call it before removing the form in a single-page app.

form.destroy();

Values

getValue(name) → any

Current value of a field. Same as form.values[name].

setValue(name, value, options?)

options: { notify?: boolean = true }

Changes a value and refreshes the screen. With notify: false, onFieldChange is not called (the timer uses this).

form.getValue('u2Voltage');            // "478"
form.setValue('u2Voltage', '480');      // updates the input and everything that depends on it
form.setValue('actualHours', 1.25, { notify: false });

refresh()

Redraws everything from form.values: recalculates formulas, updates every field, then every widget. setValue calls it for you; call it yourself only after writing to form.values directly.

Object.assign(form.values, valuesFromCrm);
form.refresh();

getData() → object

Everything needed to store the report: values, attachment details and unit statuses. This is also the body submit() sends. Shape: getData() payload.

const data = form.getData();
data.reportStatus;      // "review"
data.units[0].status;   // { status: "fail", label: "Red — deficiency found", started: true }

Sending

submit() → Promise<object | null | { queued: true } | undefined>

Sends getData() to config.submission.url.

  • Success: returns the JSON response (or null), calls onSubmitSuccess, and deletes the local draft unless it was saved later.
  • Offline mode, and offline or a temporary server error: stores it in the outbox, calls onSubmitQueued, returns { queued: true }.
  • Any other failure: calls onSubmitError and throws.
  • No submission in the config: returns undefined.
const result = await form.submit();
if (result?.queued) {
  showToast('No connection. The report will be sent automatically.');
}

syncNow() → Promise | undefined

Sends waiting offline reports now. Does nothing when offline mode is off, the device is offline, nothing is waiting, or a sync is already running.

await form.syncNow();

Callbacks

How the form tells the website that something happened. Pass them as constructor options.

}

onWorkflow(action, data, form)

After a workflow button passes validation and the status has changed. data already carries the new status. Return a promise and the button stays disabled until it settles. Throw (or reject) and the previous status is put back.

onWorkflow: async (action, data, form) => {
  await form.submit();   // throws if the CRM refuses → status rolls back
}

onSubmitSuccess(response, form)

After the CRM accepted a report: from submit(), and again for each queued report the outbox later delivers.

onSubmitQueued(data, form)

The report could not be sent now and was saved in the outbox (offline mode only).

onSubmitError(error, form)

A report was not accepted and will not be retried: a failure in submit() that isn't queued (with offline mode off, that's any failure), the outbox could not be written, or the server refused a queued report (it stays stored, marked failed). error.status holds the HTTP code for server errors.

Offline & sync

Technicians work in plant rooms and basements with no signal. This page explains what keeps working, where data is kept, and when reports are sent.

Three layers

LayerKeepsTurned on by
Service workerThe page's files: HTML, CSS, JavaScript.serviceWorkerUrl option + offline.enabled
IndexedDBThe data: drafts with photos, the outbox, a copy of the config.offline.enabled + storage: "indexedDB"
localStorageDrafts without photos, when IndexedDB isn't in use or fails.Always available

A day on site

  1. Opening the page with no signal

    The service worker serves the stored page files. The config download fails, so the copy saved on the last visit is used. The status bar reads "You're offline. Your answers stay on this device."

  2. Filling it in and saving

    Everything works as normal. Save draft stores the values and the photos in IndexedDB. Closing the browser loses nothing that was saved.

  3. Submitting with no signal

    submit() sees the device is offline and puts the report in the outbox. The status pill still changes to Review, onSubmitQueued runs, and the bar shows "1 report waiting to be sent."

  4. Back in signal

    The report is sent automatically: when the browser reports it's online again, every 30 seconds while something is waiting, when the page next opens, or when the user taps Send now. Each delivery calls onSubmitSuccess, and the local draft is deleted unless it was saved after the report was made.

When is a report retried?

What happenedTreated asResult
No network (fetch throws)temporaryStays in the outbox; retried.
HTTP 408, 429, 500, 502, 503, 504temporaryStays in the outbox; retried.
Any other HTTP error (400, 401, 404, 501…)refusedKept but marked failed and not retried; onSubmitError runs; the bar asks the user to contact support.

Reports are sent oldest first, and sending stops at the first temporary failure, so the CRM always receives them in order. If two tabs have the form open, a browser lock lets only one of them send, so nothing is sent twice.

How the service worker chooses

  • Which files: after the page loads, it sends the worker the list of files it just used. Requests made by code (API calls, the config JSON) are data and are left out. There's no file list to maintain.
  • Network first: online, stored files are always checked with the server, so a new release reaches users immediately. If the network doesn't answer within 4 seconds, the stored copy is used.
  • Never-visited pages: opened offline, they show a short "You're offline" page.

Inspecting it

In Chrome DevTools, open Application:

  • IndexedDB → AccurexDynamicForms: drafts (one per form id), outbox (waiting and failed reports, with the exact request), configs (offline copies by URL).
  • Cache storage → accurex-dynamic-form-v1: the stored page files.
  • Service workers: tick "Offline" to test without unplugging anything.

Limits

Each device must open the page once with a connection. Service workers need https (or localhost). Photos are kept in drafts but not uploaded, because the submission is JSON.

Deploy to the website

A checklist for putting the form on the corporate website, and the reasons behind each item.

Checklist

  1. Serve the package files

    Keep Accurex-DynamicFormRenderer.js, the CSS and src/ together. Load the entry with <script type="module">.

  2. Use https

    Required for the service worker, and for the clipboard on the Copy button.

  3. Place the service worker correctly (scope)

    A service worker only controls pages in its own folder and below; this is called its scope. Put service-worker.js in the same folder as the form page, or higher. If it must live deeper, e.g. /assets/accurex/service-worker.js for a page at /startup-report/, the server must send this header with that file:

    Service-Worker-Allowed: /

  4. Stop browsers caching the form config

    Have the CRM's config API send Cache-Control: no-cache. Otherwise a browser may keep showing an old version of the form after the CRM changes it.

  5. Allow cross-origin calls, if the CRM is on another domain

    The CRM must answer with Access-Control-Allow-Origin for the website's origin. Submitting JSON triggers a preflight, so the submission URL must also answer OPTIONS and allow the Content-Type header.

  6. Check the Content Security Policy

    Formulas and status rules are calculated with Function() after a strict character check. A CSP without 'unsafe-eval' blocks this: calculated fields then show 0 and status rules stay grey, with console warnings. Allow it on the form page, or avoid formulas and status rules.

Several forms on one page

Give each its own container and its own new DynamicFormRenderer(). Registries are shared, which is usually what you want. Drafts and the outbox are keyed by form id, so two forms with the same id share a draft; give them different ids.

Releasing a new version

Upload the new files. The service worker checks every stored file with the server, so users get the new code on their next visit. To force-delete everything stored on every device (e.g. after renaming many files), change CACHE_NAME in service-worker.js.

Browser support

Current versions of Chrome, Edge, Safari and Firefox, on desktop and mobile. The code uses ES modules, optional chaining and IndexedDB. Web Locks and service workers are used when available and skipped otherwise.

Guides

Security model

What the package does to stay safe with configuration from the CRM, and what it leaves to the website.

Config text is never HTML

Labels, titles, help text and option names are written with textContent through the el() helper; the package never puts config text into innerHTML. A label containing <script> is shown as those characters, not run.

Formulas and conditions

Before anything is calculated, every field name is replaced by a number, and the result must contain only digits, spaces and + - * / ( ) . < > = ! & |. With no letters or quotes left, no code can be injected. Anything else returns 0 (formulas) or false (conditions).

Data on the device

Drafts, photos and queued reports are stored unencrypted in the browser, like any website data. On shared tablets, use Discard draft after submitting, or clear site data. A successful submission removes the draft automatically.

Network

  • submit() sends no Authorization header; same-origin cookies are sent as normal. For token authentication, the CRM API needs to accept the site's session cookie, or the website sends the report itself from onWorkflow using form.getData() (without the outbox).
  • onDataPull lets the website add headers when fetching unit data.
  • The service worker stores only same-origin GET files the page used, never API responses.
  • The Email button only opens the user's email app; nothing is sent without the user.

Guides

Troubleshooting

Symptoms, causes and fixes, most common first. Open the browser console first: the package logs a clear message for almost every problem.

The page is blank

  • The script tag is missing type="module".
  • The page was opened as file://. Serve it, e.g. python3 dev-server.py.
  • "container not found": the selector doesn't match an element that exists when the script runs.
  • "could not load the form configuration (HTTP 404)": check configUrl.

JSON changes don't show up

  • The browser cached the config: send Cache-Control: no-cache from the API, or hard-reload.
  • A saved draft was restored: values come from the draft. Click Discard draft.

A field shows as a plain text box

Its type is misspelled or not registered. The console names the field.

A question never turns green

  • It has no evaluation, so it's never judged.
  • Values are compared exactly: "yes" is not "Yes".
  • Tolerance fields stay grey until both numbers are entered; percentage rules also stay grey when the reference is 0.

A calculated field shows 0

  • Field names must be in braces: {actualHours}.
  • The formula contains something other than numbers and operators. Check the console.
  • The site's Content Security Policy blocks Function(). See Deploy.

Two units share answers

Their fields have the same name. Prefix names with the unit id (u1Belt, u2Belt).

"Pull from CAPS" does nothing

  • The identity fields need prefill.field naming the key in the response.
  • source must match a key in dataSources; otherwise the action goes to onAction.
  • If the button returns to its label, the request failed; the console shows why.

A report stays "waiting to be sent"

  • The server is unreachable or returning 5xx. It is retried every 30 seconds; Send now tries immediately.
  • "could not be sent: the server refused it": the CRM answered with a 4xx. Inspect the entry in IndexedDB (outbox, error field).

The page doesn't open offline

  • serviceWorkerUrl isn't set, or behavior.offline.enabled isn't true.
  • The page isn't on https.
  • service-worker.js is in a deeper folder than the page, so the page is outside its scope. See Deploy.
  • The page has never been opened online on this device.
