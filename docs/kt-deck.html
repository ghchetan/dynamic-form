Business rule: draft, then review, then approved or rejected. Technically the status is one more value in form.values, so it is saved in drafts and sent with the report like any other field. Accurex Dynamic Form KT · 6

This is the heart of the business logic. Every tracked field gets one of four statuses. Those roll up: a section shows answered over total and turns red if anything inside is red; a unit's tab dot does the same for the whole unit; and every red or yellow field lands in the deficiency list with a View link that jumps to it. The tolerance example is a real field from the config: overload setting against nameplate FLA, green within 5 percent, yellow within 15.

PART 2

A tour of the code

About 3,200 lines of plain JavaScript modules in src/. No framework, no bundler, no npm install. The browser loads the files as they are.

Part 2. The good news: the codebase is small and has no build step. Everything under src is ES modules loaded straight by the browser. One CSS file, one entry file, one service worker. If you can read plain JavaScript, you can read all of it in a day.

One class, DynamicFormRenderer, owns everything. On the left are the things that feed it: the CRM's form JSON, the host page that creates it and passes callbacks, and the service worker that caches the page's files. THE ONE RULE

All data lives in form.values

User types

form. setValue()

form.values

form. refresh()

Screen

refresh() step 1

Calculated fields work out their numbers first, so later steps see fresh values.

refresh() step 2

Every field updates its own look: input value, status chip, selected button.

refresh() step 3

Every widget redraws what it collects from many fields: tab dots, progress, deficiencies.

Debugging tip: if the screen looks wrong, type form.values in the console. Fields never keep their own copy.

Accurex Dynamic Form KT · 9

If you remember one slide, remember this one. All data is in one object, form.values, keyed by field name. Inputs call setValue; setValue stores the value, fires onFieldChange, and calls refresh. Refresh is a full pass in three steps: recalculate, then every field, then every widget. It's deliberately simple: no diffing, no hidden subscriptions. The form is small enough that redrawing everything on each keystroke is cheap.

FORM.RENDER()

What happens when the form opens

1

Load the JSON from configUrl, or take the config object. Unwrap { form }.

6

Load the saved draft for this form id, if there is one.

2

Stop timers and syncing left from an earlier render, then reset state.

7

buildForm(): header, top sections, unit tabs, reviewer, action bar. Each field registers its default.

3

Set header values: reportStatus starts as "draft", plus the job title.

8

applyDraft(): saved values overwrite the defaults, for fields that still exist.

4

Read the layout first, because fields need the column count.

9

refresh() once, so every input and widget shows its value.

5

Read offline settings: choose the draft store, and create OfflineSync for IndexedDB.

10

Send reports left in the outbox. Set up the service worker in the background.

Accurex Dynamic Form KT · 12

Walk through render() in DynamicFormRenderer.js, top to bottom. Two order details matter. Layout is read before building because a field's column span is capped at the form's column count. And the draft is applied after buildForm, because building is what registers every field's default value; the draft then overwrites only names that still exist, so a config change never brings back stale fields. render() can be called again to rebuild; discardDraft does exactly that.

Accurex Dynamic Form KT · 13

BaseField has the whole lifecycle; subclasses usually override only renderControl, and maybe refresh. SelectField is the shortest example to copy. Two special cases. ToleranceField owns two value names, reference and reading, which is why registerField loops over getDefaultValues. CalculatedField writes straight into form.values in recalculate instead of calling setValue, because setValue calls refresh, which calls recalculate again: an endless loop.

Accurex Dynamic Form KT · 14

This is the design decision that keeps the code small. There's no switch statement over types anywhere. Four plain objects map a type word from the JSON to code. To add a signature field, write SignatureField.js and add one line to FIELD_TYPES. Unknown types fail soft: a field becomes a text box, a section becomes a card, an action goes to the host page's onAction, and an evaluation becomes gray with a console warning.

RULES

Two ways to judge an answer

evaluation: a named rule

{ "type": "expectedValue",
"expectedValue": "Yes" }

Picks a function from EVALUATORS. Makes the field tracked: it counts in progress and in the deficiency list.

statusRules: conditions

{ "when": "value <= 0",
"status": "pass" }

The first true condition wins. It only colours the input, for example the hours variance.

utils/formula.js: maths from the CRM, made safe

Field names become numbers, then only digits and operators may remain. With no letters left, no code can get in.

Accurex Dynamic Form KT · 15

A common confusion: evaluation versus statusRules. evaluation is a named rule like expectedValue, valueMap, exactMatch or percentTolerance; it makes a field tracked. statusRules is a list of conditions written in the JSON; it only colours the field. Formulas and conditions come from the CRM, so formula.js replaces every name with a number and then rejects anything that isn't digits or operators before evaluating. That check is why it's safe to use Function here.

ACTIONS

What the buttons do

workflow: Submit, Approve, Reject

  1. Required fields empty? Outline them red and stop.
  2. Disable the button, so a double-click can't send twice.
  3. Set the new status.
  4. Await the host's onWorkflow, which usually calls form.submit().
  5. If that fails, put the old status back.

dataPull

Fills model and serial: onDataPull, else dataSources URL, else onAction.

timer

Adds one second a time to actualHours. Start, pause, resume.

email · print · save

mailto from templates; window.print(); saveDraft().

Accurex Dynamic Form KT · 16

Workflow is the important one; it's in actions/workflowAction.js. The order matters: the status changes before onWorkflow, so getData sends the new status, and it's rolled back if the host throws. Data pull tries three sources in order; the host's callback comes first so a site can add auth headers. The timer writes with notify false, so onFieldChange doesn't fire every second. Email builds a mailto link from templates, and can use deficiencyStatusText.

OFFLINE MODE

Three layers keep a technician working

service-worker.js

The page opens

  • Stores only the files the page just used
  • Network first; stored copy after 4 s
  • Change CACHE_NAME to wipe every device

offline/draftStores.js

Drafts are kept

  • localStorage: values only
  • IndexedDB: values and photos
  • Same save, load, remove on both
  • IndexedDB fails? Falls back

offline/OfflineSync.js

Reports wait

  • Sends on open, when back online, every 30 s, or on Send now
  • Oldest first
  • A Web Lock lets one tab send

Switched on by behavior.offline in the config, plus serviceWorkerUrl on the page for the first layer.

Accurex Dynamic Form KT · 17

Offline is the most complex part, so split it into three. Files: the service worker caches exactly what the page loaded, network first with a 4-second timeout, so a release reaches users immediately. Data: drafts go to IndexedDB with photos, or localStorage without. Reports: the outbox in IndexedDB, sent by OfflineSync. The Web Lock stops two open tabs from sending the same report twice. The page must be on https or localhost and opened once online.

FORM.SUBMIT()

Four ways a submit can end

getData() becomes a plain request object: { url, method, headers, body }

Plain, not a fetch Request, so it can be stored in IndexedDB and sent again later.

Known offline

Don't try. Put it in the outbox, return { queued: true }, call onSubmitQueued.

Sent

Delete the draft, unless it was saved after this report. Call onSubmitSuccess.

Temporary failure

No network, or 408, 429, 5xx. Queue it and retry later.

Refused

For example 400. Retrying won't help. Call onSubmitError and throw.

Queueing needs offline mode with IndexedDB. Without it, every failure is reported straight away. Photos are kept in drafts, but submit sends only their names and sizes.

Accurex Dynamic Form KT · 18

submit() is short, but every branch matters. isTemporaryFailure in core/http.js decides: fetch throws TypeError for no network, and 408, 429 and the 5xx codes are temporary. Anything else is a real refusal. The draft rule is subtle: after a successful send we delete the draft only if it was saved before the report was made, so work the technician did after queueing is not lost. Known limit: submission is JSON, so photos are sent as names and sizes only.

HOUSE RULES

Keep these when you change the code

Never innerHTML for config text

Use el() from utils/dom.js. It sets textContent, so CRM text can't inject HTML.

One copy of every value

Only form.values. A field reads its value; it never stores it.

Screen updates go in refresh()

No hidden listeners that change the page on their own.

Storage errors never break the form

Every draft-store method catches and logs.

Status words live in constants.js

A typo becomes undefined, which is easy to spot.

Fail soft on unknown config

Fall back and warn in the console. Don't throw.

Accurex Dynamic Form KT · 19

These rules aren't written in one place in the code, but every file follows them. The first one is a security rule: config text comes from the CRM, so it always goes in as textContent. The second and third are what make the codebase easy to debug. Also keep the comment style: each file starts with a plain-English comment explaining its job and a config example. Reviewers will expect new files to do the same.
