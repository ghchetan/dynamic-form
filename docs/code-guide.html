      Before you start

      What you should already know

      Basic JavaScript: variables, functions, objects, arrays and loops. Everything else you will meet (modules, classes, async/await, closures) is explained in chapter with examples from this codebase. You don't need React, a build tool or npm. This project uses none of them.

      Run it on your machine

      git clone https://github.com/ghchetan/dynamic-form.git
cd dynamic-form
python3 dev-server.py

      Open http://localhost:8080/sample.html. Then open your browser's developer tools (⌥ ⌘ I on a Mac, F12 on Windows) and keep the Console tab open while you read.

      The big picture

      The CRM decides what the form asks. This code decides how it looks and behaves. Nobody writes HTML for a form: the code reads a JSON description and builds the page from it.

      1 · Configurationaccurex-startup-report-config.jsonWhich questions, which rules, which buttons. Comes from the CRM API.
      2 · Frameworksrc/Reads the configuration, builds the page, judges answers, saves and sends.
      3 · Host pagesample.htmlThe website page. Says where to draw the form and what to do on Submit.

      What happens when the page loads

      Follow this once with the debugger and the rest of the codebase will make sense. Each step names the function that does it.

      1. sample.html loads Accurex-DynamicFormRenderer.jsThe browser downloads it and every file it imports from src/. The entry file puts the class on window.
      2. new DynamicFormRenderer({ container, configUrl, … })The constructor only stores the options. Nothing is drawn yet.
      3. render() → loadConfig()Downloads the JSON from the CRM (or uses an offline copy).
      4. resetState(), setHeaderValues(), getLayout()Empties everything from a previous build and reads the layout.
      5. chooseDraftStore(), new OfflineSync()Decides where drafts live and whether there's an offline outbox.
      6. buildForm()Creates the header, sections, unit tabs, reviewer card and action bar. Every field in the JSON becomes a field object and registers its default value.
      7. applyDraft()If a saved draft exists, its values replace the defaults.
      8. refresh()Every field and widget draws its current state: chips, colours, totals.
      9. offlineSync.start(), setUpOfflinePage()Sends reports left from last time and stores the page's files for offline use.

      Here is that sequence in the real code. Read the comments; they say the same thing.

      1. this.providedConfig || await loadConfig(...): if the page passed a config object, use it; otherwise download it. await pauses render() until the download finishes, without freezing the page.
      2. this.offlineSync?.start(): the ?. means "only if offlineSync exists". In online-only mode it's null and the call is skipped.
      3. setUpOfflinePage(...) has no await on purpose: storing files for offline use shouldn't delay showing the form.

      Reading the import lines…

      Three things to notice:

      • utils/ and constants.js import nothing from the project. They're the foundation, safe to use anywhere.
      • fields/ imports only constants, evaluators/ and utils/. A field knows nothing about sections, buttons or offline storage, so field types can be written and tested on their own.

      JavaScript you will meet

      Modern JavaScript features used throughout the code, each with a short example. Skim it now and come back when something looks unfamiliar.

      Modules: import and export

      Each file is a module. It shares things with export and uses other files' things with import. Paths are relative and must end in .js, because the browser loads them directly.

      // src/utils/format.js
export function isEmpty(value) { /* ... */ }

// src/fields/BaseField.js
import { isEmpty } from '../utils/format.js';

      That's why the page needs <script type="module">: only module scripts may use import.

      Classes, extends and super

      A class is a blueprint for objects. extends means "start from this other class"; super(...) runs the parent's constructor or method. Field types use this: SegmentedField starts from BaseField and changes only what's different.

      export class SegmentedField extends BaseField {
    constructor(config, form, context) {
        super(config, form, context);   // let BaseField set up config, form, context…
        this.showsStatusChip = true;    // …then change one setting
    }
}

      Arrow functions and this

      Inside a normal function, this depends on who calls it. When the browser calls an event listener, this would be window, not our object. An arrow function (() => …) keeps the this of the place it was written. That's why event handlers in this code are arrow functions:

      // src/offline/OfflineSync.js — `this` stays the OfflineSync object
this.handleOnline = () => {
    this.form.refresh();
    if (this.autoSync) this.syncNow();
};
window.addEventListener('online', this.handleOnline);

      ?. and ??

      this.callbacks.onFieldChange?.(name, value)   // call it only if the website passed one
this.config.layout?.columnSpan                // undefined instead of an error if there's no layout
this.config.defaultValue ?? ''                // '' only when defaultValue is null or undefined
      Pitfall: ?? is not ||

      0 || 5 is 5, but 0 ?? 5 is 0. Use ?? for defaults when 0, false or '' are real answers. A checkbox's false or an amp reading of 0 must not be replaced by a default.

      Destructuring and default parameters

      // Pull properties out of an object, with a default for the whole object:
setValue(name, value, { notify = true } = {}) { ... }

form.setValue('u2Voltage', '480');                    // notify is true
form.setValue('actualHours', 1.25, { notify: false }); // notify is false

      Spread: ...

      const sections = [...(this.config.sections || [])];  // a copy of the array…
sections.sort((a, b) => (a.order || 0) - (b.order || 0)); // …so sorting doesn't change the config

values: { ...this.values }                            // a copy of an object

      async, await and Promises

      Downloading, reading IndexedDB and waiting for a timer take time. A Promise is an object meaning "the answer will arrive later". Inside an async function, await waits for it without freezing the page. Errors arrive as exceptions you catch with try/catch.

      async function loadReport() {
    try {
        const response = await fetch('/api/report');   // waits, page stays responsive
        return await response.json();
    } catch (error) {
        console.error('Could not load the report', error);
    }
}

      Map, Set and Object.entries

      this.fieldsByName = new Map();          // key → value, with .get(), .set(), .has()
this.fieldsByName.set('u4Mark', field);
this.fieldsByName.get('u4Mark');

for (const [name, value] of Object.entries({ a: 1, b: 2 })) { … }   // loop over an object

      Closures

      A function remembers the variables around it when it was created, even after the outer function has finished. The section code relies on this: each section's refresh remembers its own elements.

      function renderCounter() {
    const label = document.createElement('span');   // lives on inside refresh()
    function refresh(count) { label.textContent = count + ' items'; }
    return { element: label, refresh };
}
const counter = renderCounter();
counter.refresh(3);   // still updates the same label

      You'll see this pattern again in chapter.

      Check yourself: why must event handlers here be arrow functions?

      Because the browser calls them, and with a normal function the value of this would be the window or the element, not our object. this.form would then be undefined. An arrow function keeps this from where it was written.

      The main class

      DynamicFormRenderer is the conductor. It builds the page, owns every value, and tells everything else when to update. Every other part of the code gets a reference to it, usually called form.

      The front door

      The page loads only one file. It makes the class available in two ways and exports the registries, so a website can add its own field types without editing the package.

      What the form remembers

      All state lives in a handful of properties, reset at the start of every render(). The most important line is the first: all values live in this.values, a plain object of name → value.

      Two ways things join the form

      Fields join by calling registerField(), which also stores their starting values. Blocks that show information collected from many fields (deficiency list, progress chips, tab dots) join with addWidget().

      1. if (!(name in this.values)): the first field to claim a name sets its default. Header values such as reportStatus were set earlier by setHeaderValues(), and are not overwritten.
      1. It returns widget.element so you can write shell.append(this.addWidget(renderHeader(this))) in one line: register it and put it on the page.
      2. A section may return null (for example, no reviewer in the config). addWidget(null) returns null, and appendChildren() skips it.

      The loop: setValue → refresh

      This is the heart of the framework. There is exactly one way to change a value, and after every change everything redraws from this.values.

      1. Step 1 runs before step 2 so that a calculated value like "Variance" is up to date before anything displays it.
      2. widget.refresh?.(): some widgets (a plain card) have nothing to update, so they have no refresh. The ?. skips them.
      Why redraw everything?

      Updating only "what changed" is faster, but every new feature must then remember what to update, and forgetting is how bugs happen. Redrawing from one source of truth is always correct, and with about 85 values it takes well under a millisecond.

      Building the page

      buildForm() creates the page top to bottom. Read it next to the demo and you'll see each block appear in the same order.

      Check yourself: you set formRenderer.values.u4Mark = 'CP-9' in the console. Why doesn't the tab change?

      Nothing called refresh(). Changing the object directly skips the loop. Run formRenderer.refresh() and the tab updates, or use formRenderer.setValue('u4Mark', 'CP-9'), which does both and also tells the website through onFieldChange.

      Building HTML safely

      Every element on the page is created with one small helper, el(), instead of writing HTML strings.

      1. element.textContent = text puts text in as text. If a CRM label contains <img src=x onerror=alert(1)>, the page shows those characters instead of running them. Using innerHTML with config text would run it. This is called an XSS (cross-site scripting) attack.
      2. appendChildren skips null, so optional parts can be written inline: section.title ? el('h3', …) : null.
      Pitfall

      A plain <button> inside a <form> submits the form and reloads the page. Always create buttons with button(), which sets type="button".

      Fields

      Each question in the form is a field object, made from a class in src/fields/. All field classes share one parent, BaseField, which does everything common, and each type changes only what's different.

      From JSON to the right class: the registry

      A registry is a plain object that maps a name from the JSON to the code that handles it. To support a new field type, you add one line here.

      1. An unknown type still works: it falls back to a text box and warns in the console. A typo in the CRM never breaks the whole page.
      2. new FieldClass(...): FieldClass is a variable holding a class, chosen at runtime from the registry. Classes are values in JavaScript.

      BaseField draws the frame, subclasses fill it in

      render() fixes the order of the parts. Subclasses override single parts, mostly renderControl(). This is a classic design pattern called a template method.

      1. Every field type gets status chips, the red "required" outline, statusRules colours and photo thumbnails for free, just by calling super.refresh().

      A whole field type, start to finish

      SegmentedField is the Yes · No · N/A row. It's short, and it shows every idea in this chapter.

      1. constructor: asks for a status chip and prepares a list for its buttons.
      2. labelTargetId() returns null: there's no single input for the label's for attribute to point at.
      3. renderControl(): each button just calls this.form.setValue(...). The button doesn't change its own colour; refresh() does that, like everything else.
      4. refresh(): calls super.refresh() first, then marks the chosen button. aria-pressed tells screen readers which one is selected.

      A field with two values

      A tolerance field stores a reference and a reading. It overrides getDefaultValues() to return both names, and the form registers both.

      A field that calculates

      Pitfall: infinite loops

      setValue() calls refresh(), and refresh() calls recalculate(). If recalculate() used setValue(), the page would loop forever and freeze. That's why it writes to form.values directly. The comment above the method warns about exactly this.

      Check yourself: which methods would a new "rating 1–5" field need?

      Only renderControl() (draw the five buttons, each calling setValue) and refresh() (call super.refresh(), then highlight the chosen score). Label, help text, status chip, photos and progress tracking all come from BaseField. Then add one line to FIELD_TYPES. The docs walk through it in Add a field type.

      Rules and statuses

      Three small modules decide what's good and what isn't. None of them touch the page. They take data in and return an answer, which makes them easy to read and easy to test.

      Evaluators: is this answer OK?

      Another registry. The JSON says "evaluation": { "type": "expectedValue", "expectedValue": "Yes" }, and type picks the function.

      Roll-ups: how is the whole unit doing?

      A pure function gets everything it needs as arguments and returns a result, with no side effects. That makes it easy to test: same input, same output. Notice the shape too: a list of early returns, most important first. Read it top to bottom like a checklist.

      Formulas without the danger

      Calculated fields run formulas like {actualHours} - {expectedHours} that come from the CRM. Running text as code is normally dangerous, so the code first replaces field names with numbers and then refuses anything that isn't digits and operators.

      1. The safety comes from ONLY_NUMBERS_AND_OPERATORS: after the check, no letters remain, so no function or variable can be named. Function(...) only ever sees arithmetic.
      2. try/catch turns a malformed formula into a warning and a safe result (0 or false) instead of a crash.

      Sections and widgets

      Fields are classes; page blocks are plain functions. Each one builds its elements and returns an object with two things:

      return {
    element,   // what to put on the page
    refresh,   // optional: called after every change, to update what this block shows
};

      That small object is a widget. The section registry works exactly like the field registry: SECTION_TYPES maps "card", "deficiencySummary", "hoursTracker" and "equipmentStatusSummary" to their functions.

      A complete widget: the accordion

      One collapsible section inside a unit tab, with its "3/7" progress chip. Notice how refresh and setOpen use body, head and fields long after renderAccordion has returned: that's a closure (chapter).

      1. const context = { unit, section: { id: section.id, open: () => setOpen(true) } }: every field in this accordion gets a function that opens it. Later, "View" in the deficiency list calls field.context.section.open() without knowing anything about accordions.
      2. refresh() asks summarizeFields() from core/status.js for the numbers. The widget only displays them; the rules live elsewhere.

      A performance trick: skip when nothing changed

      The site timer calls refresh() every second. Rebuilding the deficiency list every second would swap its "View" buttons out from under the user's finger. So the list first builds a short text "signature" of what it would show, and does nothing if it matches last time.

      Buttons and actions

      Every configured button (Save draft, Email, Start timer, Submit for review…) has a type, and a third registry maps it to a function.

      1. Unknown types aren't errors: they're handed to the website's onAction callback, so a site can add special buttons without changing the package.

      Workflow: try, catch, finally

      "Submit for review" changes the status, then asks the website to send the report. If sending fails, the status is put back. finally runs whether it worked or not, so the button is always re-enabled.

      Timers: setInterval

      1. The interval id is stored in form.timers so a second click can stop it, and so destroy() can stop every timer. A timer that's never cleared keeps running after the form is gone.
      2. { notify: false } stops the website from receiving an onFieldChange call every second.

      Working offline

      Technicians work in basements without signal. Three browser features keep the form working:

      Browser featureStoresCode
      IndexedDBDrafts with photos, the outbox of unsent reports, a copy of the configsrc/offline/
      localStorageDrafts without photos, when IndexedDB isn't in usesrc/offline/draftStores.js
      Service workerThe page's files, so it opens with no networkservice-worker.js

      Turning events into promises

      IndexedDB is old and reports results through events (onsuccess, onerror). database.js wraps those events in Promises once, so the rest of the code can simply await.

      1. databasePromise is kept in a module variable, so the database is opened once and shared by every call.
      2. onupgradeneeded runs the first time on a device and creates the "tables" (object stores).

      Same interface, two storages

      Drafts can live in IndexedDB (with photos) or localStorage (text only). Both store objects have the same three methods, save, load and remove, so the form doesn't care which one it got. This is the strategy pattern.

      The outbox and sync

      When submit() can't reach the server, the report goes into the outbox. OfflineSync sends it later: when the browser says it's online again, every 30 seconds, or when the user taps "Send now".

      1. for…of with await sends one report at a time, oldest first, so the CRM receives them in order.
      2. A temporary failure (no network, server down) returns and tries again later. A refusal (e.g. HTTP 400) is kept but marked failed, so one bad report can't block the others forever.

      The service worker

      A service worker is a script the browser keeps running in the background for a site. It can answer the page's requests itself. Ours answers from saved copies when the network is down. It runs separately from the page, so it can't see form or the DOM; the page talks to it with postMessage.

      1. "Network first": always try for the newest file, so a release reaches users straight away, but fall back to the saved copy after 4 seconds or when offline.
      2. event.waitUntil(...) tells the browser to keep the worker alive until the copy is saved, even after the answer has been sent.

      Which files get saved? The page tells the worker, using the browser's list of everything it downloaded:

      Styles

      • One stylesheet, Accurex-dynamic-form.css. Every class starts with dfr- ("dynamic form renderer"), so it can't clash with the website's own CSS.
      • Colours are variables at the top (--dfr-brand, --dfr-pass…). A website can restyle the form by overriding them.
      • JavaScript picks classes, CSS picks looks. The code says `dfr-chip dfr-${status}`, producing dfr-chip dfr-red, and the stylesheet decides what red looks like.
      • Layout comes from the config through two variables, --dfr-max-width and --dfr-columns, set on the form by src/core/layout.js.
      • Showing and hiding uses the hidden property (element.hidden = true), not inline styles.

      3 · Add a "range" rule (20 minutes)

      Voltage to the exhaust fan should be between 460 and 500 V. Add an evaluator so the config can say:

      { "name": "u2Voltage", "label": "Voltage to fan", "type": "number", "unit": "V",
  "evaluation": { "type": "range", "min": 460, "max": 500 } }
      Show a solution

      Add one function to EVALUATORS in src/evaluators/index.js:

      /** Pass when the number is between min and max, e.g. { "type": "range", "min": 460, "max": 500 }. */
range(rule, value) {
    const number = Number(value);
    if (!Number.isFinite(number)) return FIELD_STATUS.NONE;
    return number >= rule.min && number <= rule.max ? FIELD_STATUS.PASS : FIELD_STATUS.FAIL;
},

      Because the field now has an evaluation, it counts in the EF-1 progress chip, and 430 V shows up in the deficiency list. No other file changes.

      4 · Explain a behaviour (10 minutes)

      Start the site timer. actualHours changes every second, but a website listening to onFieldChange isn't called. Why?

      Show the answer

      toggleTimer calls form.setValue(…, { notify: false }), and setValue only calls onFieldChange when notify is true. Otherwise the website would be called once a second for as long as the technician is on site.

      Glossary

      Configuration (config)
      The JSON from the CRM that describes one form: fields, rules, units, buttons.
      Field
      One question, and the object (made from a BaseField subclass) that draws it and judges its answer.
      Value name
      A field's key in form.values, from its name. Tolerance fields have two.
      Tracked field
      A field with an evaluation rule. It counts in progress chips and can be a deficiency.
      Status
      green, yellow, red or gray for a field; pass, caution, fail or pending for a section or unit.
      Deficiency
      A tracked field whose status is red or yellow.
      Evaluator
      A function that turns an answer into a status, picked by evaluation.type.
      Unit
      One piece of equipment (CP-1, HD-1, EF-1, MUA-1), shown as a tab.
      Mark
      A unit's display name, taken from its identity field whose name contains "mark".
      Widget
      An object { element, refresh } for a page block that shows information collected from many fields.
      Registry
      An object mapping a type from the JSON to code: FIELD_TYPES, SECTION_TYPES, ACTION_HANDLERS, EVALUATORS.
      Refresh
      Redrawing everything from form.values after a change.
      Draft
      A copy of the answers (and, offline, photos) saved on the device with "Save draft".
      Outbox
      Reports saved in IndexedDB because they couldn't be sent yet.
      Service worker
      A background script that serves saved copies of the page's files when there's no network.
